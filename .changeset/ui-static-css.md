Experimental: the runtime side of build-time css extraction. Compiled output can register a module's extracted rules with `registerStaticCss` and set the values of their CSS variables with `toCssValue`, both exported from every entry. A node whose styles were all extracted renders a plain element with the static classes and variables merged before its own `className` and under its own `style`, without Emotion or a theme hook. A node with css left over renders as today, with the static classes added. At a call site with one spread, the node keeps its static classes unless the spread brings a CSS key, `css`, `as` or `theme`; then it renders as the call site would uncompiled. A layout factory's call site that the compiler merged with the factory's initial props, marked with a fingerprint of them, uses its props as given when the fingerprint is the factory's own, so its initial props do not come back as runtime css. A class's rules reach the page when a node using it first renders, as Emotion's do. In the browser they go into four bucket sheets right before the tags of the Emotion cache MeoNode renders into, in that cache's container, so a cache that prepends, a shadow root or another document gets them where its own rules are. A server render sends the classes its nodes use as React hoistable styles, once per request, and the browser does not insert again what the server sent. In development, a theme token that extracted styles reference and the active theme does not define is reported as it is for the same styles uncompiled, except that for an element under one of the app's own components it is reported in the browser console only, not by the server. Output without the new markers renders exactly as before.
